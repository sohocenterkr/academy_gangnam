# Stage 5.5: Atomic Optimistic Locking Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the application-level "SELECT, compare in JS, then UPDATE" optimistic-locking pattern — used by every `PATCH` route in this codebase — with a genuinely atomic, single-statement DB-level check, across all six places it currently exists. This closes a real TOCTOU race that has been identified and parked in Stage 4's final review, Stage 5 Task 3's review, and Stage 5's own final review — three times across two stages — and is now a hard gate before any further stage adds a seventh copy of the pattern.

**Architecture:** The current pattern is: `SELECT` a row, compare its `updatedAt` (as a JS string) against the client-supplied `expectedUpdatedAt` in application code, then `UPDATE ... WHERE id = :id` unconditionally. Two concurrent requests that both pass the SELECT-compare step before either commits its UPDATE will both succeed, silently last-write-wins. The fix moves the version check into the UPDATE's own `WHERE` clause — `WHERE id = :id AND updated_at = :expected` — so only one of two racing requests can ever match a row, and the other gets zero rows back, which the code turns into `409 VERSION_CONFLICT`. This is a single atomic SQL statement per request; there is no window between check and write.

**A precision trap this plan must not walk into:** every affected table's `updated_at` column defaults to `defaultNow()` at the schema level, which uses Postgres's own `now()` — a function with **microsecond** precision. Every `INSERT` in this codebase relies on that default rather than setting `updatedAt` explicitly. JavaScript's `Date`, by contrast, cannot represent sub-millisecond precision. So today, when a freshly-created row's `updatedAt` round-trips through `db.insert(...).returning()` → JSON → `.toISOString()` → back to the client → `new Date(...)` on a later `PATCH`, both the client and the server's own JS-side comparisons only ever see the millisecond-truncated value — which is why the *current* string-based comparison (`before.updatedAt.toISOString() !== parsed.expectedUpdatedAt`) has worked correctly. But a **DB-level** `WHERE updated_at = :expected` comparison happens in Postgres, against the column's *actual stored* value — which, for any row created via `defaultNow()`, may carry non-zero microseconds the JS side never saw. Naively adding the WHERE-clause fix without also fixing this would make the very first edit of almost every row in the system fail with a false `409`, and would break essentially every existing "updates X with optimistic locking" test in this codebase, since every test fixture is created via `defaultNow()` and then immediately patched using its own just-returned `updatedAt`. **Every task in this plan must therefore also make each affected table's `INSERT` set `updatedAt` explicitly via `new Date()`** (matching what every `UPDATE` in this codebase already does), so `updatedAt` is millisecond-precision-only for every row created from here on. Pre-existing rows in the local dev DB that were created before this fix ships may see one false `409` on their very first post-fix edit — a one-time, self-healing, non-destructive edge case (a refresh-and-retry fixes it permanently for that row) that is acceptable for a dev database with no production users yet, and is not worth a data-migration to work around.

**Tech Stack:** Same as prior plans — Drizzle ORM (`drizzle-orm/node-postgres`, a real `pg.Pool`-backed driver with genuine transaction support — already confirmed by Stage 5's final review), Express 5, Zod, Vitest, Supertest.

**Spec:** [`../../../academy_automation_final_development_prompt.md`](../../../academy_automation_final_development_prompt.md) §14.3 ("수정 API는 `updated_at` 또는 version 기반 낙관적 잠금을 사용합니다") is the binding requirement this plan actually delivers on — every prior stage's PATCH route claimed to implement this but only did so at the application level, not atomically.

**Prior plans:** This plan touches code originally built across three prior plans — [`2026-08-14-stage3-academic-reference-data.md`](2026-08-14-stage3-academic-reference-data.md) (`schools.ts`, `gradeLevels.ts`, `academySettings.ts`), [`2026-08-15-stage4-guardians.md`](2026-08-15-stage4-guardians.md) (`guardians.ts`), and [`2026-08-15-stage5-students.md`](2026-08-15-stage5-students.md) (`students.ts`, `studentGuardians.ts`) — but is not itself a new feature; it is the cross-cutting hardening pass those three plans' own final reviews all called for.

## Global Constraints

- API envelope and error codes are unchanged: `409 VERSION_CONFLICT` on a version mismatch, same `{ error: { code, message, requestId } }` shape as today.
- Every `PATCH` route's `expectedUpdatedAt` field changes from `z.string()` to `z.iso.datetime()` in its Zod schema — this rejects a malformed/non-ISO string with a clean `400 VALIDATION_ERROR` at the parse layer, before it ever reaches a query, and guarantees `new Date(parsed.expectedUpdatedAt)` is never an `Invalid Date`.
- Every affected table's `INSERT` statement must explicitly set `updatedAt: new Date()` (see "A precision trap" above) — this is not optional polish, it is required for the WHERE-clause fix to work correctly against fixtures and real data alike.
- The atomic UPDATE's `WHERE` clause is always `and(eq(table.id, id), eq(table.updatedAt, expectedUpdatedAt))` (or the transaction-scoped equivalent for `studentGuardians.ts`). A zero-row result from that UPDATE is treated as `409 VERSION_CONFLICT` — the preceding `SELECT` (kept only for the 404 check, and, where applicable, for reading fields like `phoneNormalized` needed by duplicate-check logic) is no longer the source of truth for versioning and must not compare `updatedAt` itself anymore.
- Existing behavior that has nothing to do with versioning — unique-violation handling, foreign-key-violation handling, duplicate-phone-warning flows, audit logging, the `student_guardians` primary-uniqueness transaction logic — is preserved exactly as-is; this plan only changes how the version check itself is performed.
- No separate test DB — every server integration test hits the real local dev `DATABASE_URL` and must clean up every row it creates, following each file's own already-established `cleanup()` pattern. Never touch the real bootstrapped super-admin.
- `npm run check` must be clean after every task.
- At least one genuine **concurrent**-request integration test (firing two `PATCH` requests with `Promise.all`, not sequentially) must exist proving the second writer gets `409` — the existing "stale retry" tests only prove correctness *after* a completed prior write, not atomicity under a real race, and were the specific gap the final reviewers asked to be closed.
